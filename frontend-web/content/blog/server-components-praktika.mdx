React Server Components изменили подход к рендерингу. Но в команде часто возникает вопрос: «когда серверный, когда клиентский?». Разберём, как мы это решаем на практике.

## Что такое Server Component

Server Component рендерится на сервере, в браузер уходит уже готовый HTML и сериализованное дерево. Никакого JS-бандла для этого компонента в клиенте — он просто не нужен. Импорт серверных модулей (БД, файловая система, секреты) — без проблем, потому что код никогда не дойдёт до браузера.

По умолчанию в App Router все компоненты — серверные. Чтобы сделать клиентский, в начало файла добавляется `"use client"`. Это директива не для одного компонента, а для всего модуля и его импортов вниз по дереву.

## Когда Server Component — правильный выбор

Чтение данных, рендер статики, формирование HTML с серверной логикой. Любая страница списка, карточка товара, статья блога, главная — всё это Server Components.

Преимущества: меньший JS-бандл (часто 30-50% от Pages Router), быстрее TTI и FCP, безопасный доступ к секретам и БД, удобный async/await прямо в компоненте.

```tsx
async function ProductPage({ params }) {
  const product = await db.product.findUnique({ where: { slug: params.slug } });
  return <Product data={product} />;
}
```

## Когда нужен Client Component

Любой интерактив: формы с состоянием, кнопки с onClick, drag-and-drop, анимации, использующие refs, react-spring или framer-motion. Хуки `useState`, `useEffect`, `useReducer` работают только в клиентских компонентах.

Не пытайтесь сделать всё клиентским «на всякий случай» — это убивает основное преимущество архитектуры. Лучше: серверный layout, серверная страница, и точечно подключаются клиентские островки для интерактива.

## Композиция: серверный родитель, клиентский ребёнок

Базовый паттерн: родительский Server Component делает запросы и передаёт данные через props в клиентский компонент. Клиентский компонент уже может работать со state, формами, обработчиками.

```tsx
async function Page() {
  const data = await getData();
  return <ClientForm initialData={data} />;
}
```

Обратное (клиентский родитель, серверный ребёнок) — невозможно напрямую. Можно через children: клиентский компонент принимает `{ children }`, а в него прокидывают серверный JSX из вышестоящего серверного компонента.

## Сериализация props

Передавая props из серверного в клиентский, помните: они сериализуются через React Flight Protocol. Можно передавать примитивы, массивы, объекты, Date, Map, Set, BigInt. Нельзя — функции (кроме Server Actions с `"use server"`), классы, React-элементы из неэкспортированных компонентов.

Передача больших объектов из БД — окей, но фильтруйте лишнее. Не нужно передавать весь юзер-объект с паролем хешем, выберите нужные поля заранее.

## Server Actions: формы без API

Server Actions — серверные функции, которые можно вызывать из клиентских форм. Удобно для CRUD-операций без отдельных API-роутов.

```tsx
async function createPost(formData: FormData) {
  "use server";
  const title = formData.get("title");
  await db.post.create({ data: { title } });
  revalidatePath("/posts");
}
```

Валидация — на сервере, всегда. Не доверяйте `FormData` от клиента: проверяйте через Zod, проверяйте права, проверяйте rate limit.

## Граничные случаи

Серверный компонент не может использовать context, который определён в клиентских провайдерах. Workaround: оборачиваете дерево в клиентском провайдере, серверные компоненты передаются как children.

`useSearchParams` и `useRouter` — клиентские хуки. На сервере используйте `searchParams` через props страницы и `redirect`/`notFound` из `next/navigation`.

## Итого

Правило: всё серверное по умолчанию, клиентское — точечно для интерактива. Это даёт минимальный JS-бандл, быстрый рендер, безопасный доступ к данным. Через 2-3 проекта команда привыкает мыслить такими границами, и code review становится проще.
