Через 2–3 года любой бот сталкивается с морально устаревшим стеком: фреймворк не развивается, библиотеки уязвимы, разработчики не хотят это поддерживать. Полная переписка кажется единственным выходом, но это самый рискованный путь. Разберём стратегии миграции, которые реально работают.

## Когда мигрировать

Признаки, что пора:

- Фреймворк не получает обновлений больше года.
- Bot API ушёл вперёд: появились Stars, Business Bots, новые типы апдейтов — а вы не можете их использовать.
- Зависимости Python 2 / Node 12 — на которые уже не выпускают патчи безопасности.
- Каждое изменение требует двух дней и трёх молитв.
- Никто из новых разработчиков не хочет браться.

Если ничего из этого нет, возможно, миграция не нужна — стек работает, бот живёт.

## Стратегии миграции

### 1. Rewrite from scratch

Самая радикальная — полностью переписываем бот. Плюсы: чистый код. Минусы: полгода работы и риск, что новый бот будет хуже старого по UX, потому что забыли половину edge cases.

Подходит, если:

- Бот совсем простой (5–10 сценариев).
- Старый код документирован достаточно, чтобы повторить логику.
- Есть бюджет на 3–6 месяцев параллельной разработки.

### 2. Strangler Fig

Постепенно заменяем функционал по кусочкам. Старый бот продолжает работать, новый бэкенд берёт на себя сначала один сценарий, потом два, потом всё.

Технически:

- Новый бэкенд работает рядом со старым.
- Webhook отправляет апдейты в роутер, который решает, кому идти.
- Постепенно сценарии переносятся, флаг переключает между старой и новой реализацией.
- Через 3–6 месяцев старый код можно удалить.

Плюсы: меньше риска, новые фичи можно делать сразу на новом стеке. Минусы: сложнее в управлении, нужна дисциплина.

### 3. Параллельный новый бот

Создаём `@yourapp_v2_bot`, постепенно переводим пользователей. Старый бот продолжает работать, рассылает приглашение в новый.

Плюсы: чистый разрыв, новый бот без legacy. Минусы: пользователи теряют историю, могут не перейти.

Подходит для критичных миграций (например, переезд на новое юрлицо), когда чистый старт важнее истории.

## Миграция aiogram 2 → 3

Самая частая миграция в Python-экосистеме. Главные различия:

- **Хэндлеры**. Декораторы стали проще: `@router.message(F.text == "/start")` вместо `@dp.message_handler(commands=["start"])`.
- **Объекты Telegram**. Pydantic-классы вместо словарей. Доступ через атрибуты, не индексы.
- **FSM**. `StatesGroup` остался, но `State` теперь без `set_data`/`get_data` в старом виде.
- **Middleware**. Полностью другой API на `BaseMiddleware`.
- **Filters**. Магический объект `F` для фильтров вместо длинных классов.

План миграции:

1. Создаёте отдельный бранч.
2. Обновляете `aiogram` до 3.x.
3. Перенос идёт «снизу вверх»: сначала middleware и общие хэндлеры, потом сценарии.
4. Запускаете старый и новый бот параллельно (на разных токенах) и смотрите регрессы.
5. Переключаете webhook на новый бот.

Срок реальной миграции среднего бота (20–30 хэндлеров) — 2–4 недели работы одного разработчика.

## Миграция Node telebot/Telegraf → grammY

В Node-экосистеме чаще всего мигрируют с Telegraf на grammY. Хорошая новость — grammY концептуально близок к Telegraf. Различия:

- Чистая типизация TypeScript из коробки.
- Плагины (conversations, runner, menu) вместо самописных решений.
- API roles: `bot.command`, `bot.on("message:text")`, `bot.callbackQuery` — выразительный синтаксис.

Срок миграции — 1–3 недели для бота среднего размера.

## Миграция базы данных

Если меняете не только фреймворк, но и БД (MongoDB → Postgres, MySQL → Postgres):

- Создаёте новую БД параллельно.
- Запускаете двойную запись: новые операции пишутся в обе БД.
- Через инструмент миграции переносите старые данные.
- Сверяете консистентность.
- Переключаете чтение на новую БД.
- Останавливаете запись в старую.

Это занимает 2–8 недель в зависимости от объёмов. Никогда не делайте миграцию «одним SQL-скриптом ночью» — это путь к катастрофе.

## Что не должно потеряться

При любой миграции сохраняйте:

- **FSM-состояния пользователей**. Если у юзера сценарий на полпути, он не должен начинать заново.
- **История платежей**. Все транзакции, чеки, возвраты.
- **Реферальные связи**. Кто кого пригласил.
- **Сегменты и метки**. Если у вас CRM-фичи, правильная миграция меток обязательна.
- **Логи и аналитика**. Не теряйте исторические данные — без них непонятно, как менялись метрики.

Если что-то теряется, сначала уведомите пользователей, а потом мигрируйте — иначе шквал жалоб.

## Параллельный запуск

Самый безопасный паттерн — фича-флаги. Один пользователь обслуживается старым кодом, другой — новым. Ошибки нового видны на малой выборке, не на всех.

Технически в БД у пользователя поле `version: "v1" | "v2"`. Webhook на основании этого поля направляет апдейт в нужный обработчик. По мере уверенности увеличиваете долю на v2.

## Документация и тесты

До миграции:

- Опишите все сценарии текстом, как ТЗ. Часто оказывается, что половину функционала никто не помнит точно.
- Соберите датасет реальных диалогов для регресс-тестирования.
- Покройте критичный функционал интеграционными тестами.

Без этого миграция превращается в «угадайку», и баги вылезают на пользователях.

## Подводные камни

- **Изменение `chat.id`**. Если меняете бот на новый токен, `chat_id` перерегистрируется как другой объект (хотя сам ID числовой не меняется). Связь с пользователем сохраняется.
- **Старые webhook URLs**. После переноса не забудьте удалить старый webhook через `deleteWebhook`.
- **Зависимости fp-моделей**. Если вы использовали ML-модели старой версии, проверяйте, что они корректно работают на новой.
- **Часовые пояса в БД**. После миграции с MySQL на Postgres даты часто сдвигаются — заложите буферный день на сверку.

## Итого

Миграция Telegram-бота — это управляемый риск, а не одноразовая авантюра. Лучшие стратегии: strangler fig для крупных проектов, параллельный запуск со флагами для малых, чистая переписка только если сценариев совсем немного. Сохраняйте FSM-состояния, платежи и реферальные связи, документируйте сценарии до миграции, тестируйте на малой выборке. Срок реальной миграции — от пары недель для смены фреймворка до нескольких месяцев для полной переархитектуры.
