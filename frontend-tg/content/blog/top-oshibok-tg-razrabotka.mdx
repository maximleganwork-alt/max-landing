Большинство ботов умирают не из-за плохой идеи, а из-за технических и продуктовых ошибок, которых легко было избежать. Собрали топ проблем, с которыми регулярно встречаемся в чужих проектах при аудите и поддержке.

## Долгий webhook

Самая распространённая ошибка — синхронная обработка тяжёлых задач прямо в webhook. Бот получает апдейт, идёт в LLM, ждёт 8 секунд, отвечает.

Чем плохо:

- Telegram повторяет запрос, если ответа нет за 60 секунд — пользователь получает дубли сообщений.
- Сервер забивается медленными воркерами.
- При ошибке в LLM весь webhook падает, апдейт теряется.

Решение: webhook отвечает 200 за 1–2 секунды, тяжёлые задачи кладутся в очередь и обрабатываются воркерами. Стандарт — Celery/RQ для Python, BullMQ для Node, NATS для Go.

## Игнорирование ошибок Bot API

Bot API возвращает ошибки нескольких типов: 400 (плохой запрос), 401 (бот заблокирован), 403 (пользователь запретил писать), 429 (rate limit), 500 (проблемы Telegram). Многие разработчики просто `try/except: pass`.

Чем плохо:

- 403 — пользователь забанил бота, нужно пометить в БД и не слать ему рассылки.
- 429 — нужен backoff и retry, иначе вы вылетите по rate limit на час.
- 500 — нужно повторить, а не считать сообщение отправленным.

Решение: обработать каждый класс ошибок отдельно. 403 — отметить пользователя как «заблокировал», 429 — exponential backoff, остальное — логировать и алертить.

## Хранение состояния в памяти процесса

```python
user_states = {}  # глобально

@dp.message()
async def handler(message):
    user_states[message.from_user.id] = "waiting_phone"
```

Чем плохо:

- При рестарте состояние теряется — пользователь застревает посередине сценария.
- При нескольких воркерах состояния расходятся.
- Утечка памяти растёт линейно с количеством пользователей.

Решение: FSM с внешним хранилищем — Redis, Postgres, MongoDB. У aiogram это `RedisStorage`, у grammY — `@grammyjs/storage-*`, у teloxide — `RedisStorage`.

## Незащищённый webhook

Webhook без проверки подписи — открытая дверь. Любой может слать на ваш URL поддельные апдейты.

Решение:

- Передавать `secret_token` в `setWebhook`. Telegram будет слать его в заголовке `X-Telegram-Bot-Api-Secret-Token`.
- Проверять заголовок на каждом запросе.
- Слушать только https, не http.
- Блокировать прямые запросы без правильного User-Agent.

## Один токен на все окружения

Боевой токен в dev, в тестах, у трёх разработчиков на ноутбуках. Через какое-то время кто-то отправит тестовое сообщение реальным пользователям, или утечёт ключ.

Решение: отдельный бот на каждое окружение (`@yourapp_dev`, `@yourapp_staging`, `@yourapp_bot`), отдельные токены, отдельные БД. Боевой токен — только в production-среде, доступ — у одного DevOps.

## Отсутствие FSM на сложных сценариях

Сценарий с 5+ шагами на if/else быстро превращается в нечитаемый код. Каждое новое условие добавляет ветку, ошибки растут.

Решение: явный FSM с состояниями. Каждое состояние — отдельный обработчик. Переход — через установку состояния. Это и читаемо, и тестируемо.

## Игнорирование callback_query

`callback_query` — это нажатие inline-кнопки. Если не вызвать `answerCallbackQuery`, пользователь видит «крутилку» бесконечно.

Решение: после обработки кнопки — всегда `bot.answerCallbackQuery(callback_query.id)`, даже пустым. Это часто упускают и удивляются «у пользователя залипла кнопка».

## Плохой парсинг команд

`if message.text == "/start"` ломается на `/start@your_bot` (когда бот в группе) и на `/start ref_123` (с payload).

Решение: использовать встроенные парсеры фреймворка (aiogram `CommandStart`, grammY `commandHandler`) или регулярки `^/start(?:@\w+)?(?:\s+(.+))?$`.

## Хранение чувствительных данных в логах

Логи с полным сообщением пользователя, паролями, токенами, телефонами. Через полгода логи разрастаются на гигабайты, и любая утечка превращается в инцидент.

Решение:

- Маскировать телефоны, email в логах.
- Не логировать тело платёжного callback целиком.
- Не логировать полные тексты сообщений в чате.
- Ротация логов с TTL 14–30 дней.

## Отсутствие health-check

Бот может молча зависнуть: процесс жив, но не отвечает. Без health-check вы узнаете об этом из жалоб пользователей через час.

Решение: endpoint `/health`, который проверяет ключевые зависимости (БД, Redis), возвращает 200 если ок. Внешний мониторинг (UptimeRobot, Healthchecks) пингует каждые 60 секунд и алертит при первом провале.

## Платежи без идемпотентности

Пользователь нажал «Оплатить» дважды. Без ключа идемпотентности на стороне бота два платежа уйдут в кассу.

Решение: каждый платёж имеет уникальный `idempotency_key` (`order_id` + timestamp), бэкенд проверяет — если такой ключ уже создал инвойс, возвращает существующий, не создаёт новый.

## Игнор edited_message

Пользователь отредактировал своё сообщение. Бот по умолчанию это не видит, и сценарий рассыпается («я писал 5, а потом исправил на 10, бот всё равно посчитал 5»).

Решение: либо явно слушать `edited_message`, либо явно сообщать пользователю, что редактирование не учитывается.

## Один бот на множество ниш

Бот «и записать на маникюр, и купить курс, и записаться к врачу» — расфокусированный. Пользователь не понимает, что он умеет, и метрики низкие.

Решение: бот = один продукт. Если ниш несколько, делайте отдельных ботов с общим бэкендом.

## Отсутствие тестов на сценарии

Боты часто пишут «без тестов, потом добавим». Через полгода код такого, что любое изменение ломает 3 сценария.

Решение: интеграционные тесты на FSM-сценарии (имитируем серию апдейтов, проверяем ответы), unit-тесты на бизнес-логику. CI прогоняет тесты на каждый PR.

## Итого

Топ ошибок: долгий webhook без очереди, отсутствие FSM с внешним хранилищем, незащищённый webhook без `secret_token`, один токен на все окружения, игнор `callback_query` и `edited_message`, отсутствие health-check и идемпотентности на платежах, плохие логи. Большинство этих проблем решаются на этапе проектирования, и стоят недорого. Когда они вылезают на пользователях — стоят на порядки дороже. Хорошая архитектура — лучшая инвестиция в долгую жизнь бота.
