Любой нелинейный сценарий в боте — это конечный автомат. Пользователь идёт по шагам: ввод имени, ввод телефона, подтверждение. Между шагами бот должен помнить, на каком этапе он находится и какие данные уже собрал. Эту память называют FSM, и от её устойчивости зависит, будет ли бот работать в проде или ронять диалоги при каждом перезапуске.

## Что такое FSM в контексте бота

**Конечный автомат (FSM)** — это набор состояний и переходов между ними. В боте состояние = «на каком шаге сценария находится пользователь». Переход — это сообщение или нажатие кнопки, которое двигает пользователя дальше.

Пример простой записи на услугу:

1. `idle` — диалог не запущен.
2. `awaiting_service` — ждём выбор услуги.
3. `awaiting_date` — ждём дату.
4. `awaiting_time` — ждём время.
5. `awaiting_phone` — ждём телефон.
6. `confirmation` — показываем сводку, ждём подтверждения.
7. `done` — заявка принята.

Каждое состояние знает, какие апдейты валидны. Если пользователь в `awaiting_phone` пришлёт фото, бот не должен ломаться — он мягко напомнит, что ждёт телефон.

## Где хранить состояние

Простейший вариант — в памяти процесса. Работает, пока бот не перезапустится. Любой деплой ломает все активные диалоги — это неприемлемо для продакшена.

Рабочие варианты:

- **Redis** — самый частый выбор. Быстро, переживает перезапуски, есть TTL. Ключ обычно `fsm:{user_id}`, значение — JSON со state и data.
- **Postgres** — медленнее, но надёжнее, можно делать сложные запросы. Подходит для длинных сценариев с историей.
- **Гибрид** — Redis для горячего состояния, Postgres для финальных данных и истории.

Для большинства проектов Redis с persistence (AOF + RDB) закрывает требования.

## Структура данных

Минимальный объект FSM:

```
{
  "state": "awaiting_phone",
  "data": {
    "service": "стрижка",
    "date": "2026-05-12",
    "time": "14:30"
  },
  "started_at": "2026-05-01T10:00:00Z",
  "updated_at": "2026-05-01T10:02:15Z"
}
```

`data` накапливает ответы пользователя. Когда дойдём до `confirmation`, у нас будет всё нужное для создания заявки.

## Таймауты и сброс

Пользователь может начать диалог, отвлечься на час и вернуться. Что должен сделать бот?

Варианты:

- **Long TTL** (сутки или неделя) — пользователь продолжит с того же места. Хорошо для сложных длинных сценариев (заполнение анкеты).
- **Short TTL** (15–30 минут) — после таймаута состояние сбрасывается, при следующем сообщении бот стартует диалог заново. Хорошо для быстрых сценариев (запись, заказ).

Можно комбинировать: на 15 минуте напомнить «вы хотели записаться, продолжим?» с кнопками «да/нет». Если ответа нет 30 минут — сбрасываем.

## Параллельные сценарии

Что если пользователь в середине записи на услугу нажимает /menu? Варианты:

1. **Игнорировать команды** во время сценария.
2. **Прерывать** — отменить запись, начать новый сценарий.
3. **Спрашивать** — «вы прерываете запись, продолжить?».

Третий вариант самый user-friendly, но усложняет код. На практике хватает явного выхода через команду /cancel и игнора прочего.

## Версионирование

Сценарии меняются. Если у пользователя в Redis висит старый state `awaiting_color`, а вы переименовали его в `awaiting_color_v2`, бот может упасть. Решений два:

- **Сбросить все активные FSM** при деплое мажорной версии.
- **Пометить версию** в ключе (`fsm:v2:{user_id}`), старые состояния просто не подхватываются и таймаутятся.

Второй вариант мягче, но требует дисциплины при изменении сценариев.

## Тестирование

FSM — отличный кандидат на юнит-тесты. Не нужны моки MAX API: тестируем чистую функцию `transition(state, event) → new_state`. Разделение FSM-логики от транспорта позволяет тестировать сценарии без бот-фреймворка вообще.

## Антипаттерны

- Хранить state в `chat_data` бот-фреймворка без персистентности — потеряете при рестарте.
- Мешать FSM и бизнес-логику в одном классе — превращается в неподдерживаемую кашу.
- Не валидировать ввод на каждом шаге — пользователь введёт «мама» вместо номера, и заявка уйдёт битой.
- Один глобальный FSM на всех — каждый пользователь должен иметь изолированное состояние.

## Итого

FSM — фундамент любого нетривиального бота в MAX. Корректное хранение состояния (обычно в Redis), TTL и обработка таймаутов, версионирование при деплоях, тестируемость в отрыве от транспорта — стандартные требования к проду.
