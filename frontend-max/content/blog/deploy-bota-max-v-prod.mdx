Между «бот работает у меня на ноуте» и «бот в проде» — большой технический разрыв. В этом разрыве — Docker, CI/CD, миграции БД, секреты, мониторинг и нулевой даунтайм при релизах. Разберём типовой стек для бота MAX, который выдерживает реальную аудиторию и обновления раз в неделю.

## Контейнеризация

Бот в проде — это Docker-образ. Преимущества:

- Один и тот же артефакт от dev до prod.
- Простое обновление: новый образ → перезапуск.
- Изоляция зависимостей: версии Python/Node/Go не зависят от хоста.

Базовые правила:

- *Multi-stage build* — отделить зависимости компиляции от рантайма.
- *Distroless* или *alpine* для финального образа — минимум поверхности атаки.
- Явный non-root пользователь.
- HEALTHCHECK — Docker сам перезапустит при провале.

Финальный образ обычно 30–80 МБ для Go, 100–200 МБ для Python с минимизацией.

## Хранилища

Для бота нужны:

- **Postgres** — пользователи, сценарии, бизнес-данные.
- **Redis** — FSM, кэш, очереди.
- **Объектное хранилище** (S3-совместимое — Yandex Object Storage, Selectel) — для вложений и файлов.

Оба stateful-сервиса лучше брать как managed: Yandex Managed PostgreSQL, Selectel Cloud Database. Бэкапы, репликация, мониторинг — из коробки. Самостоятельная эксплуатация Postgres — отдельная работа на полставки.

## Хостинг в РФ

Для соответствия 152-ФЗ персональные данные пользователей-россиян хранятся в РФ. Подходящие площадки:

- Yandex Cloud — широкий спектр managed-сервисов, есть VPC и приватные сети.
- Selectel — аналогично, плюс bare metal по запросу.
- VK Cloud — естественный выбор, если уже работаете в экосистеме VK.
- Любой VPS-провайдер с серверами в РФ — для небольших ботов.

Из-за блокировок зарубежных сервисов хостинг в РФ ещё и проще операционно: меньше проблем с доступностью платежей и API.

## CI/CD

Минимальный пайплайн:

1. На каждый pull request — линт, тесты, сборка образа.
2. На merge в main — пуш образа в registry, выкат на staging.
3. Ручное подтверждение — выкат на прод.

Инструменты:

- **GitHub Actions** — если код на GitHub. Самый низкий порог входа.
- **GitLab CI** — если на собственном GitLab или у клиента.
- **Yandex Cloud CI** или Cloud Build — встроенный в облако.

Хранение образов — Yandex Container Registry или собственный Harbor.

## Миграции БД

Каждый релиз может включать изменение схемы БД. Правила:

- Миграции в коде, в репозитории, версионируются.
- Сначала выкатываем миграцию, потом — новый код, который её ожидает.
- Миграции **обратно совместимы** в течение одного релиза. Удаление колонки = две миграции (одна добавляет nullable, выкат, другая удаляет).
- Никогда не запускаем миграции вручную в проде — только через CI.

Инструменты: `golang-migrate`, `alembic` (Python), `Prisma Migrate`, `liquibase`.

## Нулевой даунтайм

Бот не должен пропускать апдейты во время деплоя. Подходы:

- **Rolling update** — оркестратор (docker compose, k8s) сначала запускает новый контейнер, потом гасит старый. Между ними короткий период, когда оба работают.
- **Graceful shutdown** — при SIGTERM бот заканчивает обработку текущих апдейтов и только потом выходит. Реализуется через context cancellation в Go или signal handler в Python.

Для webhook нужен балансер (nginx) перед ботом, который держит соединение пока контейнер запускается. Для long polling — оркестратор сам справляется.

## Секреты

Токен бота, ключи API, пароли БД — никогда не в коде, не в Dockerfile и не в docker-compose под git. Варианты:

- `.env` на сервере с правами 600 — минимальный.
- HashiCorp Vault — для серьёзных установок.
- Yandex Lockbox — managed-секреты в облаке.
- Docker secrets / k8s secrets — для оркестраторов.

CI получает секреты из защищённого хранилища (GitHub Secrets, Vault), пробрасывает в команду деплоя.

## Бэкапы

Сценарий «всё пропало» должен иметь план восстановления. Минимум:

- Postgres — managed-сервис делает регулярные бэкапы автоматически. Проверять восстановление раз в квартал.
- Конфиги и инфраструктура — в git, проверяем `terraform plan` чисто.
- Объектное хранилище — версионирование на бакете, чтобы можно было откатить случайное удаление.

## Что обычно забывают

- **Лимит ресурсов** на контейнер — без них утечка памяти убивает соседей.
- **Часовой пояс** — внутри контейнера UTC, в логах UTC, отображение пользователю — в локальном.
- **Health check** для Bot API — проверять можно через `getMe`, который не требует апдейтов.
- **Тестовый прогон** деплоя — staging должен быть похожим на прод по конфигу.

## Итого

Прод-деплой бота в MAX — это сборка из контейнеризации, managed-БД, CI/CD с миграциями, секретов в защищённом хранилище и graceful shutdown. Всё это собирается за пару недель работы DevOps и потом окупается тем, что релизы становятся скучным процессом, а не ночным героизмом.
