Тестирование бота отличается от тестирования веб-сервиса. Здесь нет контроллеров и роутов — есть FSM, асинхронные апдейты и внешние API. Без автотестов любая правка превращается в лотерею: где-то отвалится сценарий, и узнаете об этом по жалобе пользователя. С тестами релизы становятся предсказуемыми, и можно безопасно рефакторить.

## Юнит-тесты сценариев

Если FSM-логика отделена от транспорта, она прекрасно тестируется в изоляции. Тест выглядит так:

1. Создаём пустое FSM-состояние.
2. Прогоняем серию событий (нажатия кнопок, текстовые ответы).
3. Проверяем итоговое состояние и накопленные данные.

Никакого MAX API не требуется — это чистая функция «вход → выход». Покрытие 80%+ на FSM — реалистичная цель.

## Тестирование handler'ов

Handler'ы (обработчики апдейтов) обычно сидят на бот-фреймворке. Чтобы их тестировать, есть два пути:

- **Mock-бот** — фреймворк подменяется на класс, который собирает вызовы `send_message` в список. Дальше проверяем, что бот вызвал нужные методы с нужными аргументами.
- **Тестовая обёртка** — фреймворки часто дают свой test-helper (например, `aiogram-tests`).

Тест сценария «запись на услугу» проверяет:

1. На /start пришло приветствие с кнопками.
2. На нажатие «Записаться» бот спросил услугу.
3. После выбора услуги — спросил дату.
4. И так до подтверждения.

## Mock внешних API

CRM, банк, МИС — внешние сервисы, которые в тестах нельзя дёргать. Используем mocks:

- В Python — `unittest.mock` или `responses` для HTTP.
- В Go — интерфейс на адаптер, тестовая реализация.
- В Node — `nock` для HTTP, `jest.mock` для модулей.

Принцип — между бизнес-логикой и внешним API всегда стоит **наш** интерфейс/класс. В тесте подменяем его на заглушку с предзаготовленными ответами.

## Интеграционные тесты

Юнит-тесты не покажут проблему «бот вроде работает, но БД не пишет». Интеграционные тесты поднимают **реальные зависимости** в контейнерах:

- `testcontainers` (Java, Go, Python) запускают Postgres и Redis на время теста.
- `docker-compose -f compose.test.yml` для более сложных сетапов.

В тесте создаём пользователя, прогоняем сценарий, проверяем, что в БД появилась запись. Эти тесты медленнее юнитов (секунды вместо миллисекунд), поэтому обычно их меньше — покрывают только критичные пути.

## Сценарные / E2E-тесты

Самые дорогие, но и самые ценные. Идея — поднять весь стек и прогнать сценарий целиком, как это сделал бы пользователь.

Реализация:

1. Поднимаем бот, БД, Redis, mock внешних сервисов.
2. Создаём симулятор пользователя — посылает апдейты в Bot API mock.
3. Гоняем последовательность действий, проверяем итоговый результат (сообщение пользователю + запись в БД + вызов внешнего API).

Хорошо подходят для регрессионного тестирования критичных сценариев (оформление заказа, оплата). Запускаются на CI ночью или раз в час, не на каждый PR — слишком медленно.

## Нагрузочное тестирование

Перед публичным запуском нужно понять, выдержит ли бот ожидаемую нагрузку. Инструменты:

- `k6` — современный, на JavaScript, удобный.
- `Locust` — Python, наглядный.
- `artillery` — Node.js.

Симулируем N виртуальных пользователей, каждый прогоняет типовой сценарий. Замеряем p95/p99 latency, ошибки, нагрузку на БД и Redis.

Что искать:

- Нелинейный рост latency при увеличении нагрузки (узкое место в БД).
- Ошибки 5xx или таймауты при определённом RPS (нехватка воркеров).
- Утечки памяти при длительной нагрузке.

Тестируем в среде, максимально похожей на прод, иначе цифры не соответствуют реальности.

## Регрессионные тесты на UX

Бот можно «сломать» не только в коде, но и в формулировках. Сценарий: меняем текст приветствия, и где-то остаётся ссылка на старое название кнопки.

Регрессионные snapshot-тесты на ключевые сценарии:

1. Запускаем сценарий.
2. Сериализуем все ответы бота в файл.
3. Сравниваем с эталоном.

При изменениях обновляем эталон осознанно через ревью.

## CI/CD

В пайплайне:

1. Линтер — `ruff`, `eslint`, `golangci-lint`.
2. Юнит-тесты — параллельно, должны пройти за минуту.
3. Интеграционные — секунды, тоже параллельно.
4. E2E — отдельный job, может идти 5–10 минут.
5. Нагрузка — отдельно, по расписанию или вручную перед релизом.

Покрытие отслеживается, но не как самоцель. 100% покрытие при кривых тестах — иллюзия безопасности.

## Антипаттерны

- Тесты, которые ходят в реальный Bot API во время CI — флакают и медленно.
- Тесты, которые зависят от текущего времени без `freeze_time`/`gomock_clock` — не воспроизводимы.
- Один большой тест на весь сценарий вместо набора маленьких — упал и непонятно, где.
- Игнорирование интеграционных тестов «потому что юниты есть» — пропустите интеграционные баги.

## Итого

Тестирование бота MAX — это пирамида: много юнитов на FSM-логику, средний слой интеграционных тестов с реальной БД и Redis, тонкий слой E2E на критичные сценарии. Плюс нагрузочные тесты перед каждым большим релизом. Эта инфраструктура окупается уже на третьем-четвёртом релизе тем, что релизы перестают быть стрессом, а становятся рутиной.
