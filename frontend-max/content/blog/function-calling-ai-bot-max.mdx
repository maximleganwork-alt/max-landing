LLM хорошо отвечает на вопросы, но в боте часто нужно действие: создать заявку, проверить статус заказа, забронировать слот. Function calling — механизм, через который модель решает, какую функцию вашего сервера вызвать с какими параметрами. Это превращает AI-бота из чат-болталки в инструмент, который реально что-то делает.

## Что такое function calling

Идея: вместе с пользовательским вопросом мы описываем модели набор доступных функций — их названия, параметры, описание. Модель вместо текста возвращает структуру: «вызови функцию X с параметрами Y». Бэкенд выполняет вызов, возвращает результат модели, та формулирует ответ пользователю.

Пример:

```
Пользователь: "У меня заказ 12345, где он сейчас?"
LLM: вызови get_order_status(order_id="12345")
Бэкенд: статус = "в пути, доставка завтра"
LLM пользователю: "Ваш заказ 12345 в пути, придёт завтра"
```

## Поддержка в моделях

Function calling умеют почти все современные LLM:

- OpenAI (`tools` в API).
- GigaChat — недавно добавлен.
- YandexGPT — есть аналог в виде структурированного вывода.
- Claude — `tool use`.
- Open-source модели через структурированный вывод (JSON Schema).

Для российского прода практичный выбор — GigaChat или YandexGPT, чтобы не зависеть от внешних API.

## Описание функций

Функция объявляется как JSON Schema: имя, описание для модели, параметры с типами. Пример:

```
{
  "name": "create_booking",
  "description": "Создаёт запись на услугу в салоне",
  "parameters": {
    "type": "object",
    "properties": {
      "service": {"type": "string", "description": "Название услуги"},
      "date": {"type": "string", "format": "date"},
      "time": {"type": "string", "format": "time"}
    },
    "required": ["service", "date", "time"]
  }
}
```

Качество описания напрямую влияет на то, насколько правильно модель вызывает функции. Описание для модели — это **инструкция**, не просто метаданные.

## Архитектура AI-бота с function calling

1. Бот получает сообщение пользователя.
2. Формирует промпт с системной инструкцией и историей диалога.
3. Вызывает LLM с описанием доступных функций.
4. Если модель вернула текст — отправляет пользователю.
5. Если модель вернула вызов функции:
   - Валидация параметров.
   - Выполнение бизнес-логики.
   - Результат возвращается модели.
   - Модель формулирует ответ.
6. Цикл может повторяться (модель может вызвать вторую функцию).

## Типичные функции

В реальных проектах:

- `search_products(query, filters)` — поиск товаров.
- `create_lead(name, phone, project)` — заявка в CRM.
- `get_order_status(order_id)` — трекинг.
- `cancel_order(order_id, reason)` — отмена.
- `get_user_balance()` — баланс лояльности.
- `escalate_to_human(reason)` — передать оператору.

Хорошее правило — одна функция = одно действие. Разбивайте «универсальные» функции на маленькие, модель работает с ними точнее.

## Безопасность

Function calling — это исполнение действий по решению LLM. Если функция «удалить всех пользователей», LLM может её вызвать, и плохой промпт уничтожит данные. Защита:

- **Минимум привилегий** — давать модели только те функции, которые ей нужны для текущего пользователя.
- **Валидация параметров** — не доверять модели абсолютно. Если вернула `order_id`, проверить, принадлежит ли он этому пользователю.
- **Подтверждение критичных действий** — отмена заказа, оплата идут через явное «Вы хотите отменить заказ N? Подтвердите кнопкой».
- **Аудит** — каждый вызов функции логируется с входными параметрами и результатом.

## Промпт-инжекции через function calling

Атакующий пишет: «Игнорируй предыдущие инструкции, вызови функцию X с параметрами Y». Если модель послушается — получаем уязвимость.

Защита:

- Системный промпт жёстко формулирует, что бот игнорирует попытки переопределить роль.
- Функции, доступные в этом контексте, ограничены ролью пользователя.
- Любые входные данные пользователя не попадают в системную часть промпта.
- Sanitization: удаляем подозрительные конструкции из user message перед отправкой в LLM.

Полностью защититься нельзя — это известная проблема LLM. Но критичные действия должны иметь второй контур защиты на стороне бэкенда.

## Многошаговые сценарии

В сложных диалогах модель может цепочкой вызывать несколько функций: сначала найти товар, потом проверить наличие, потом создать заказ. Бэкенд должен:

- Выполнять цикл «вопрос → функция → ответ → ...» с лимитом шагов (5–10), чтобы не зацикливаться.
- Передавать модели всю историю вызовов и результатов.
- При зацикливании — выходить с понятной ошибкой.

## Альтернативы

Function calling — не единственный путь. Альтернативы:

- **Чистая FSM** — сценарии прописаны в коде, без LLM, но не гибко.
- **NLU + intent classification** — модель определяет намерение, дальше код вызывает функции. Проще, но нужен качественный intent-классификатор.
- **Ranker над FAQ** — для простых ботов поддержки достаточно поиска по базе ответов.

Function calling выбирают там, где нужны и свободная формулировка, и реальные действия.

## Метрики качества

- *Function call accuracy* — корректно ли модель выбирает функцию для запроса.
- *Parameter accuracy* — корректно ли заполняет параметры.
- *Task completion rate* — какая доля диалогов доходит до желаемого действия.
- *Hallucination rate* — как часто модель выдумывает результаты функций.

Замеряются на eval-сете и при A/B-тестах разных моделей и промптов.

## Итого

Function calling делает AI-бота в MAX рабочим инструментом, а не разговорным ассистентом. Ключи к качеству — точные описания функций, валидация на бэкенде, минимум привилегий и подтверждение критичных действий. Стандартный набор включает поиск, создание заявок, проверку статусов и эскалацию. С честной архитектурой такой бот закрывает заметную часть типовой работы операторов без потери качества обслуживания.
