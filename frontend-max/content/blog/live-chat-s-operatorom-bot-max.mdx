Бот не должен закрывать 100% запросов — попытка сделать это убивает UX. Зато он отлично фильтрует типовые вопросы и переводит сложные на оператора. Разберём, как технически устроен handoff (передача диалога человеку) и что нужно для рабочего операторского места.

## Зачем нужен handoff

Хороший бот — не «вместо человека», а «впереди человека». Бот отвечает на типичные вопросы (60–80% обращений), а сложные эскалирует. Преимущества:

- **Оператор не отвлекается** на повторяющиеся вопросы — занимается только сложными кейсами.
- **Пользователь не злится** — на простой вопрос получает ответ за секунду.
- **Команда поддержки масштабируется** — один оператор закрывает в 3–5 раз больше пользователей.
- **Метрики прозрачны** — видно, какие темы бот не закрывает, что нужно дописать.

Без handoff бот превращается в раздражающий FAQ, который не решает реальные проблемы.

## Триггеры эскалации

Когда бот должен передать на оператора:

- **Явный запрос** — пользователь нажал «Соединить с оператором» или написал «Нужен человек».
- **Низкая уверенность AI** — confidence score менее порога (например, 0.7).
- **Повторная неудача** — бот два раза не понял пользователя.
- **Сложная категория** — вопросы про возврат денег, юридические аспекты, индивидуальные условия.
- **VIP-клиент** — эскалация по статусу из CRM.

В каждом случае бот сообщает пользователю «Передаю оператору, ответ в течение N минут» и ставит обращение в очередь.

## Архитектура операторской очереди

Минимальный стек:

- **Postgres** — таблица обращений: id, chat_id, user_id, статус, оператор_id, тема, приоритет, timestamps.
- **Redis** — очередь активных обращений по операторам, кеш доступности.
- **WebSocket** — для real-time апдейтов в кабинете оператора.
- **Frontend** — простая SPA на React/Vue, где оператор видит свои чаты, отвечает в них.

Состояния обращения: `created → assigned → in_progress → resolved → closed`. При каждом переходе — событие в логи и метрики.

## Как сообщения переходят между ботом и оператором

Базовый паттерн:

1. Пользователь пишет в бот → MAX доставляет апдейт → бот ловит и обрабатывает.
2. Если состояние FSM = «ожидает оператора» → бот пересылает сообщение в админку.
3. Оператор отвечает в кабинете → бэкенд формирует ответ через Bot API MAX → пользователь получает.
4. Когда оператор закрывает диалог → бот возвращает FSM в нормальный режим.

Все сообщения сохраняются в БД с маркером отправителя (бот / оператор / пользователь) и подтягиваются в историю обращения.

## Рабочее место оператора

Хорошая операторская консоль включает:

- **Очередь обращений** с приоритетами и временем ожидания.
- **Окно чата** с историей: видно и сообщения бота, и пользователя.
- **Карточка пользователя** — данные из CRM, история заказов, последние обращения.
- **Шаблоны ответов** — быстрые заготовки на типовые ситуации.
- **Заметки и теги** — внутренние комментарии, классификация.
- **Передача коллеге** — handoff между операторами.
- **Закрытие обращения** с причиной — для аналитики.

Опционально: внутренний чат между операторами, статусы (доступен / на обеде / занят), KPI-дашборд с временем реакции и оценкой пользователя.

## Интеграция с helpdesk

Если в компании уже есть helpdesk (Юздеск, Окдеск, Битрикс24 Поддержка), бот можно подключать к нему вместо собственной админки:

- Каждое обращение становится тикетом с источником «MAX-бот».
- Сообщения синхронизируются в обе стороны через webhook helpdesk.
- Оператор работает в привычном интерфейсе.

Это дешевле и быстрее, чем своя консоль, особенно для команд более 10 человек. Но возможности кастомизации меньше.

## Метрики и SLA

Что обязательно мерить:

- **Время первого ответа оператора** (TTFR) — главный показатель.
- **Время решения обращения** (TTR).
- **Доля обращений, решённых ботом** без оператора — должна расти со временем.
- **Оценка пользователя** (CSAT) — после закрытия чата бот спрашивает 1–5 звёзд.
- **Загрузка операторов** — сколько чатов одновременно в работе.

Целевые SLA для типового бизнеса: TTFR менее 5 минут в рабочее время, TTR — менее 2 часов на простые, менее 24 часов на сложные.

## Подводные камни

- **Не закрывать FSM при handoff**. Оператор закончил, а бот забыл вернуть пользователя в обычный режим. Решение — авто-возврат через таймаут бездействия.
- **Дубли**: пользователь повторно нажал «Связать с оператором», создаётся новый тикет рядом со старым. Решение — проверка активного обращения.
- **Уведомления операторам**: если новый чат не алертит — он стоит часами. Решение — звуковой/визуальный сигнал в консоли + push при отсутствии.
- **Архив переписки**: пользователь просит «дайте копию переписки». Решение — экспорт через бот или email.

## Итого

Handoff в боте MAX — это связка триггеров эскалации, очереди обращений в Postgres + Redis, WebSocket-кабинета оператора (или интеграции с helpdesk) и обязательных метрик TTFR/TTR/CSAT. Хороший бот закрывает большинство типовых вопросов и эскалирует сложные. Архитектурно реализуется за 2–3 недели и масштабируется на десятки операторов; даёт прозрачную аналитику качества поддержки.
