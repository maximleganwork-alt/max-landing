LLM сами по себе не знают вашу базу знаний — нет внутренних регламентов компании, договоров, текущих цен. Чтобы AI-бот в MAX отвечал по делу и не выдумывал, используют RAG: Retrieval Augmented Generation. Это простая идея — сначала найти релевантные документы, потом дать их модели как контекст.

## Что такое RAG в двух словах

Классическая схема:

1. Пользователь задаёт вопрос боту.
2. Бот превращает вопрос в эмбеддинг (вектор).
3. Ищет в векторной базе самые похожие фрагменты документов.
4. Подставляет их в промпт и отправляет в LLM.
5. Возвращает ответ пользователю.

Главное преимущество — модель отвечает по вашим данным, а не по «общим знаниям интернета». Можно обновлять базу без переобучения модели.

## Источники знаний

В корпоративном боте обычно подключают:

- Регламенты и инструкции в Word/PDF.
- База знаний в Confluence/Notion.
- FAQ с сайта.
- Карточки товаров и услуг.
- Историю обращений в поддержку.

Все источники проходят пайплайн: парсинг → разбиение на чанки → эмбеддинг → запись в векторную базу.

## Чанкинг

Документ длиной 50 страниц нельзя засунуть в LLM как есть. Его разбивают на чанки — фрагменты по 200–500 токенов. Подходы:

- **По параграфам** — простой, но плохо работает с длинными списками.
- **С перекрытием** (overlap) — каждый чанк включает 10–20% предыдущего, чтобы не терять контекст на границах.
- **По смыслу** (semantic chunking) — разбивка по тематическим переходам, дороже, но точнее.

Стартовать обычно стоит с чанков по 300 токенов с перекрытием в 50.

## Эмбеддинги

Эмбеддинг — это вектор фиксированной размерности (например, 768 или 1536), отражающий смысл текста. Похожие тексты дают похожие векторы.

Модели для русского языка:

- OpenAI `text-embedding-3` — качественно, но за рубежом.
- GigaChat Embeddings от Сбера — российский вариант.
- YandexGPT Embeddings — тоже доступен в РФ.
- Open-source: `e5-large`, `bge-m3` — можно хостить у себя.

Качество эмбеддинга — фундамент RAG. Плохие эмбеддинги = нерелевантные документы = плохие ответы LLM.

## Векторная база

Хранилище для векторов с быстрым поиском по косинусной близости:

- **pgvector** (расширение для Postgres) — если уже есть Postgres, не нужен новый сервис.
- **Qdrant** — российский продукт, написан на Rust, отлично работает.
- **Weaviate**, **Milvus**, **Chroma** — альтернативы.
- Yandex Cloud имеет managed-pgvector.

Для бота на 100k чанков pgvector справляется без проблем. На миллионы — стоит смотреть в сторону Qdrant или Milvus.

## Retrieval-стратегия

Простой `top-k cosine similarity` работает не всегда. Усиления:

- **Hybrid search** — комбинация векторного поиска и BM25 (классического полнотекстового). Лучше работает с именами, артикулами, числами.
- **Re-ranking** — отбираем top 50 кандидатов, прогоняем через cross-encoder, выбираем top 5. Точнее, но дороже.
- **Query expansion** — расширяем вопрос пользователя синонимами или переформулировками перед поиском.
- **Metadata filtering** — фильтр по дате, источнику, категории.

Какие комбинации применять, решается на эксплуатации: делаем eval-сет вопрос-ответ и подбираем стратегию по метрикам.

## Промпт и защита от галлюцинаций

Промпт собирается так:

```
Ты — ассистент компании X. Отвечай на основе предоставленных документов.
Если в документах нет ответа — скажи "не знаю".

Документы:
[чанк 1]
[чанк 2]
[чанк 3]

Вопрос: {user_question}

Ответ:
```

Дополнительно:

- **Цитирование** — модель должна указывать, из какого чанка взяла факт.
- **Запрет на домыслы** — явно в системном промпте.
- **Фильтр на выходе** — если ответ не содержит ссылок на документы, считаем ответ ненадёжным.

## Оценка качества

RAG нужно оценивать на специальном eval-сете: 50–200 пар «вопрос → правильный ответ». Метрики:

- *Hit rate* — попал ли нужный документ в выдачу.
- *Mean Reciprocal Rank* — на каком месте выдачи был нужный документ.
- *Answer correctness* — оценивается экспертом или GPT-as-judge.
- *Faithfulness* — соответствует ли ответ источникам.

Eval-сет обновляется по мере роста базы знаний.

## Стоимость и латентность

Одно обращение к RAG-боту — это:

1. Эмбеддинг вопроса (десятки мс).
2. Поиск в БД (десятки мс).
3. Re-ranking (опционально).
4. Запрос к LLM (1–5 секунд).
5. Стриминг ответа.

Итого 2–7 секунд до конца ответа. На предварительном этапе — статус «думаю», чтобы пользователь не нервничал.

Стоимость — порядка нескольких рублей за обращение к качественной модели. На больших объёмах кэшируем частые вопросы и/или используем дешёвую модель для простых.

## Антипаттерны

- Засовывать в промпт все 20 чанков — модель размывает фокус.
- Использовать только семантический поиск — теряем точные совпадения по числам.
- Не фильтровать персональные данные перед записью в векторную базу — попадёт в логи.
- Не обновлять чанки при изменении исходных документов — будете отвечать по старым ценам.

## Итого

RAG — стандартный способ сделать AI-бота, который отвечает по вашей базе знаний без галлюцинаций. Архитектура держится на качественных эмбеддингах, разумном чанкинге, гибридном поиске и честных промптах. На старте можно собрать MVP за пару недель на pgvector и одной из доступных в РФ моделей; потом оттачивать качество по eval-сету.
