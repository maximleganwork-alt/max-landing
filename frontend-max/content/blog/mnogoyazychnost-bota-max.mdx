Если бот рассчитан только на РФ — обычно хватает русского. Но для туристических, международных и B2B-сервисов многоязычность становится требованием. Реализовать i18n в боте можно за вечер, а можно построить устойчивую систему, которая не сломается при добавлении пятого языка. Разница — в архитектурных решениях на старте.

## Определение языка пользователя

Bot API передаёт код языка пользователя в поле локали. Это первая подсказка: если у пользователя в MAX интерфейс на русском, скорее всего, он хочет общаться на русском.

Дополнительные сигналы:

- Явный выбор через команду /language или кнопку.
- IP-геолокация (если она доступна на бэкенде).
- История прошлых сообщений (детектор языка).

Лучшая практика — сохранять выбор языка в профиле пользователя в Postgres. При первом контакте — детектируем, при сомнениях — спрашиваем кнопками с флагами.

## Хранение переводов

Самые частые форматы:

- **JSON-файлы** по языку: `locales/ru.json`, `locales/en.json`.
- **YAML** — удобнее редактировать, поддерживает многострочные тексты.
- **gettext (.po)** — стандарт для серверной разработки, подходит, если переводы делает агентство.
- **БД с админкой** — если перевод правят нетехнические люди.

Для бота на 2–3 языка хватает JSON. Для 5+ — лучше БД или хотя бы Crowdin/Lokalise с экспортом в JSON.

## Структура ключей

Плоские ключи `welcome_message` плохо масштабируются. Лучше иерархия:

```
booking:
  start: "Запись на услугу"
  ask_service: "Какую услугу выбираем?"
  ask_date: "Выберите дату"
errors:
  invalid_phone: "Телефон в формате +7..."
  generic: "Что-то пошло не так"
```

Это снимает конфликты между похожими формулировками и упрощает ревью переводов.

## Подстановки и плюрализация

Простая подстановка `Привет, {name}!` работает везде. Сложнее с *plural forms*: «1 запись», «2 записи», «5 записей». В русском три формы, в английском — две. Нативные библиотеки i18n (формат ICU MessageFormat) умеют это:

```
{count, plural,
  one {# запись}
  few {# записи}
  many {# записей}
  other {# записи}
}
```

В Python — `babel`, `Format.JS`. В Go — `nicksnyder/go-i18n`. В Node — `i18next` или `formatjs`.

## Даты, числа, валюты

«15.05.2026» в РФ и «5/15/2026» в США — разные форматы одной и той же даты. Полагаться на ручное форматирование нельзя — нужна локаль:

- Даты — `Intl.DateTimeFormat` (Node), `babel.dates` (Python), `time.Format` с локалью (Go).
- Числа — разделители тысяч и десятичных. 1,000.50 vs 1 000,50.
- Валюты — символ, позиция, число знаков после запятой.

Для бота на mnogoyazychnoy аудитории это важно: «1,500» в немецком интерфейсе — это полтора, а не полторы тысячи.

## Кнопки и команды

Тексты кнопок переводятся вместе с сообщениями. Команды (`/start`, `/help`) обычно остаются в латинице, но описание команд в меню — переводится через метод `setMyCommands` с указанием `language_code`.

Глобальные тексты (политика конфиденциальности, оферта) — отдельные документы на каждом языке. Бот должен показывать ту версию, которая соответствует выбранному языку, иначе пользователь не сможет осознанно дать согласие.

## Контент от пользователей

Что делать, если бот получает от пользователя сообщение на языке, отличном от его профиля? Варианты:

1. Проигнорировать, не угадывать.
2. Запустить детектор языка и спросить «вы хотите переключить интерфейс?».
3. Использовать встроенный в Bot API язык клиента (если изменился).

Самый безопасный — не угадывать. Дайте явную команду переключения, остальное — лишний шум.

## Тестирование

Тесты для i18n проверяют:

- Все ключи покрыты во всех локалях (нет «торчащих» английских строк в немецком интерфейсе).
- Нет лишних ключей, которые остались от старых сценариев.
- Подстановки работают корректно для всех форм plural.
- Длина переводов не ломает интерфейс (немецкий обычно длиннее русского на 30%).

Линтеры типа `i18n-tasks` (Ruby), `pyenchant` или собственные скрипты на CI закрывают это автоматически.

## Антипаттерны

- Хардкод строк в коде (`bot.send("Привет!")`) — даже на старте проекта.
- Один JSON на все языки в виде дерева `{key: {ru: ..., en: ...}}` — масштабируется плохо.
- Сборка переводов через машинный перевод без ревью — для делового контекста подведёт.
- Игнорирование RTL (арабский, иврит) — если планируется такая аудитория.

## Итого

Многоязычность в боте MAX — это не «добавить три файла», а архитектурное решение. Правильный набор: язык в профиле пользователя, иерархические ключи, библиотека с поддержкой ICU MessageFormat, локали для дат и чисел, отдельные документы для каждого языка. Сделанный с этими основами бот спокойно растёт от двух до десяти языков без переписывания.
