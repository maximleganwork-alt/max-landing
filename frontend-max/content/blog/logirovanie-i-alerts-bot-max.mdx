В разработке логи нужны для отладки, в проде — для расследования инцидентов. Бот, у которого нет нормального логирования, превращается в чёрный ящик: пользователь жалуется, но воспроизвести нельзя, потому что нет следов. Хорошая система логов и алертов экономит часы при разборе проблем и сокращает простои.

## Структурное логирование

Текстовый лог `INFO: user pressed button` бесполезен в проде. Структурный — JSON со всеми контекстными полями — позволяет фильтровать, агрегировать, строить дашборды:

```
{
  "level": "info",
  "ts": "2026-05-01T10:00:00Z",
  "msg": "fsm_transition",
  "user_id": 12345,
  "from_state": "idle",
  "to_state": "awaiting_phone",
  "request_id": "abc123"
}
```

Библиотеки: `zerolog`, `zap` (Go), `structlog`, `loguru` (Python), `pino`, `winston` (Node). Все умеют JSON-вывод с минимальным оверхедом.

## Корреляция запросов

Один пользовательский апдейт может проходить через несколько сервисов: бот → CRM → платёжка → бот. Без сквозного `request_id` или `trace_id` собрать всю цепочку в одно расследование невозможно.

При получении апдейта генерируем UUID и пробрасываем в каждый исходящий вызов через заголовок `X-Request-Id`. Все сервисы логируют его. В централизованном хранилище фильтруем по `request_id` и видим всю историю.

Полноценный distributed tracing (OpenTelemetry, Jaeger) — следующий уровень. Для большинства ботов хватает request_id.

## Что логировать

- Каждый входящий апдейт от MAX (тип, user_id, chat_id).
- Каждый исходящий вызов API (метод, latency, статус).
- Каждый переход FSM.
- Каждое создание/изменение бизнес-сущности (заявка, заказ, платёж).
- Все ошибки со стектрейсом.

Что НЕ логировать:

- Полные тексты сообщений (особенно с ПДн).
- Пароли, токены, ключи в любых вариантах.
- Полные тела платёжных webhook (там номера карт, хоть и маскированные).

При сомнениях — логируйте маску («введён номер карты ***1234») вместо полного значения.

## Где хранить логи

Варианты:

- **Loki + Grafana** — лёгкое, индексирует по меткам, дешёвое в эксплуатации.
- **ELK (Elasticsearch + Kibana)** — мощное, но прожорливое по ресурсам.
- **Yandex Cloud Logging** — управляемый сервис, не нужно держать стек.
- **Локальный stdout + ротация** — минимальный вариант для маленьких ботов.

Для прода я бы рекомендовал Loki как разумный компромисс по цене и удобству. Под капотом — те же дашборды Grafana, что и для метрик.

## Метрики

Логи отвечают на «что произошло». Метрики — на «как часто и насколько долго». Минимум для бота:

- `bot_updates_total` — счётчик апдейтов по типу.
- `bot_update_duration_seconds` — гистограмма времени обработки.
- `bot_api_call_duration_seconds` — длительность вызовов MAX API.
- `bot_external_api_duration_seconds` — длительность вызовов внешних сервисов (CRM, банк).
- `bot_errors_total` — счётчик ошибок по типу.

Экспортируется через `/metrics` в формате Prometheus. Дальше Grafana с дашбордами и Alertmanager.

## Алерты

Хороший алерт — это:

- Действенный — на него можно реагировать.
- Точный — не сработает на ровном месте.
- Срочный — требует внимания сейчас, а не «когда-то».

Базовый набор:

1. **Бот не отвечает** — нет успешных апдейтов более 5 минут.
2. **Ошибки в API MAX** — 5xx или 429 чаще порога.
3. **Падение внешних интеграций** — CRM/банк/МИС не отвечают.
4. **Нагрузка** — очередь апдейтов растёт (long polling) или 5xx на webhook.
5. **Ошибки бизнес-логики** — массовые исключения в одном сценарии.

Алерты идут в дежурный канал (отдельный чат в MAX или Telegram, Slack, корпоративная почта). Главное — чтобы их видели, а не молча накапливали.

## Дашборды для дежурного

Не «50 графиков», а 5–7 ключевых:

- Number of active users (за 5/30/60 минут).
- Error rate по сценариям.
- Latency p50/p95/p99 на обработку.
- API health (MAX, внешние).
- Очередь и нагрузка процессоров.

Дашборд должен открываться по ссылке за секунду, без логина и фильтров.

## Расследование инцидента

Сценарий: «у пользователя X не прошла оплата». Шаги:

1. По user_id ищем последние апдейты в логах.
2. По request_id поднимаем всю цепочку.
3. Проверяем ответ платёжного сервиса.
4. Сверяем с метриками: была ли деградация в этот момент.
5. Если ошибка повторяется у других — разбор инцидента и патч.

Без структурных логов и request_id это занимает часы. С ними — минуты.

## Итого

Логи и алерты — основа эксплуатации бота в MAX. Структурное логирование с request_id, метрики Prometheus, дашборды Grafana и осмысленный набор алертов закрывают большую часть инцидентов. Они становятся не блокером, а тематикой 5-минутного разбора. На старте можно обойтись простым stdout, но в проде эта инфраструктура окупается с первого же серьёзного бага.
